    utils/analysisCache.ts

    In-memory memoization for the page's expensive analysis passes.

    Why this exists

    useReadingTools.ts re-runs its whole effect — clean, split, POS, bolding, underlines — on any watched setting change, even ones unrelated to a given pass (e.g. changing lineFocusHeight still re-triggers extractKeywords() and applyPOSHighlight(), neither of which depends on line-focus at all). None of those passes previously memoized anything, so every settings tweak re-walked the DOM and re-ran compromise parsing / complexity scoring from scratch — that's the source of the "toggling anything feels slow" latency.

    Three independent stores, each keyed by something stable across an unrelated settings change but that changes when the real input changes:

    • getCachedKeywordExtraction / setCachedKeywordExtraction — keyed by the concatenated paragraph text. extractKeywords()'s result doesn't depend on boldThresholdPercent (that's applied later, in applyPhraseBolding's per-paragraph slicing) — only on paragraph text.
    • getCachedPosParse / setCachedPosParse — keyed by a single text node's exact string content, caching compromise's parsed term/tag structure. Tags don't depend on enabled/colors — only the rendering does — so a colour-only change reuses every previous parse instead of re-running nlp() across the whole page.
    • getCachedComplexity / setCachedComplexity — keyed by lowercase word, caching scoreComplexity()'s output. Shared by wordUnderlines.ts and paragraphScorer.ts, so a word scored by one is free for the other.

    Invalidation

    None of these expire on their own — sized for a single page view, not a long session. Call clearAnalysisCache when the underlying DOM content changes from under them (e.g. SPA navigation, if this content script persists across route changes rather than being re-injected per page load). I haven't seen how — or whether — this extension detects navigation, so that call site isn't wired here; it needs to go wherever that detection lives.

    What's NOT handled here

    wordSimplifier.ts's scoreComplexity itself isn't wrapped by this file — the get/set pair are cache storage only. Call sites (currently wordUnderlines.ts and paragraphScorer.ts) check the cache before calling scoreComplexity and populate it after. I haven't seen wordSimplifier.ts, so I don't know if scoreComplexity has any internal state that would make this unsafe — flagging rather than guessing there too.
