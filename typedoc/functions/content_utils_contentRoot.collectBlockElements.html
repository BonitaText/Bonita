    Function collectBlockElements

    • collectBlockElements(opts?: WalkBlocksOptions): Element[]

      Finds every "paragraph-shaped" element under opts.root.

      Deliberately matches the broad BLOCK_TAGS set rather than <p> alone — this is what fixes the Khan-Academy-class bug where body copy is entirely div-based with no <p> tags.

      Each candidate is excluded via hasBlockedAncestor called on the candidate itself, not its parent. This matters for widget markup like AP News's photo/video carousel: .CarouselSlide-info-content, .ReadMore toggles, and caption <p> tags are block-shaped divs/ paragraphs that would otherwise pass every other check, and their own class is what marks them as non-prose — checking only the parent's ancestor chain (an earlier bug here) missed exactly this case whenever the immediate parent didn't happen to repeat the widget class.

      To avoid double-counting nested containers (e.g. <div><p>…</p></div>, or Khan Academy's Perseus renderer, which wraps every real paragraph in several layers of plain <div>), a candidate is dropped if any other candidate is nested anywhere inside it, at any depth, through any kind of wrapper (inline or block) — only the innermost text-bearing candidate in a nesting chain survives. This is checked against the candidate set (post-filtering), not against direct children and not against raw BLOCK_TAGS membership. That distinction matters concretely:

      <div class="CarouselSlide-info-content">
        <span class="CarouselSlide-slideCount">1 of 7</span>
        <span class="CarouselSlide-infoDescription">
          <p>The move came after…</p>
        </span>
      </div>

      An earlier version of this dedup only inspected an element's direct children for a BLOCK_TAGS member. <span> isn't in BLOCK_TAGS, so it was invisible to that check — the outer div's direct children are both <span>s, so the div was (wrongly) treated as "innermost" and returned as its own candidate, in addition to the nested <p> two levels down (which independently qualified too, for the same reason). Any inline wrapper (<span>, <a>, <em>, …) between two block elements defeated the old dedup the same way.

      Parameters

      • opts: WalkBlocksOptions = {}

        See WalkBlocksOptions.

      Returns Element[]

      Array of block elements, in document order. May be empty.

      Known-issue-fixed

      An intermediate version of this dedup walked the check in the wrong direction: it walked up from each candidate and dropped it if an ancestor was also a candidate. For a nesting chain A > B > C where all three independently qualify — e.g. Khan Academy's stacked Perseus wrapper divs, whose concatenated text easily clears the word-count floor even though each is just a container for several real paragraphs — that inverted check keeps A (nothing above it qualifies) and drops B and C, the opposite of "innermost wins." The effect was severe: whole containers full of unrelated paragraphs, headers, and figures got treated as one splittable/scorable block, and on AP News the caption's containing widget div (which also held the byline) got kept instead of the caption <p> itself, pulling the author name into the split. The version below walks the check in the correct direction: for each candidate, walk up its ancestor chain and mark any ancestor found in the candidate set as a container — i.e. something to discard — while the original inner candidate itself is left untouched. This prunes wrapping containers, not their contents, which is what "only the innermost survives" actually requires.

      This double-candidacy was also the root cause of a caption-corruption bug in sentenceSplitter.ts: with both the outer div and the inner <p> in the result set, a bespoke internal traversal that only trusted the outer block being caption-classified — but that itself relied on this function's filtering — could still process text spanning both nested candidates inconsistently. Returning exactly one, innermost element per nesting chain removes that ambiguity at the source.

      This is the canonical list of "paragraphs" on the page. Any feature that needs to score or rank paragraph text and then later act on those same paragraphs should call this once and keep the Element references, rather than collecting text separately (e.g. a <p>-only scrape) and re-finding the elements afterward by text-matching — that split is what caused sentenceSplitter.ts to silently do nothing on <p>-free pages even after this function itself was fixed to look beyond <p>.
